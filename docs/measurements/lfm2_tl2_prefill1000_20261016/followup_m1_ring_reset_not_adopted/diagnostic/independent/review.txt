Source chain was checked against the exact frozen DSP snapshot and unchanged ARM
core: hexkl_token.c resets moe_calls once per token; graph_moe_run and the
all-resident route increment immediately before the actual MoE call. A refused
ROWS_OUT path returns before reset and decrements the graph count. Dense calls
are not this counter and cannot pass native LFM E64 eligibility. Token completion
copies graph moe_calls into the response; host checks r.rc before accumulating
it, then prints sum/e.tokens to two decimals. The LFM M1 eligibility is native
TL2, K2048/I1536/N2048, E64, one row, at most top4 active experts, SiLU, no affine;
its sole try_reset call is the one instrumented. The native path also requires
the existing feed and supported arena before reaching reset. Shared loader
warmup is M=max(512,INIT_SEQ_LEN), so it cannot add an M1 reset attempt. These are
single-prompt processes, not a same-handle multiprompt count experiment.

The diagnostic is located inside actual hexkl_dma_ring_try_reset returns.
used1 is after software indices/tail reset and immediately before return1;
the caller then skips its original 256*128-byte memset. It does not merely log
an enabled environment option. The original BSS/type-zero/incomplete-tail
fallback remains, but this model cohort exercised no fallback; existing host
lifecycle tests provide the fallback coverage, not this device observation.
