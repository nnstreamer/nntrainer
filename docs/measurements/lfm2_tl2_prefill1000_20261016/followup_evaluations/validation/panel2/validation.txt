Native TL2 paired activation-LUT candidate, 2026-10-16

Base and artifacts
  Own worktree: nntrainer-lfm2-tl2-panel2-20261016, bf10e0e04 plus DN4.
  lfm2-tl2-panel-pair-production.patch: three production files only.
  lfm2-tl2-panel-pair-tests.patch: primitive fixture, actual-worker fixture delta,
    and portable run_host_checks.sh commands.
  lfm2-tl2-panel-pair-complete.patch: production plus tests, applies AFTER DN4.
  Both deltas passed git apply --check on parent root. Root/device not modified.

Scope
  DN dispatch defaults on for Hexagon v81+, off on older/host targets.
  GU dispatch defaults off; NNTR_LFM2_TL2_PAIR_GU=1 enables the second candidate.
  Both require native TL2, M1, K2048/inter1536/N2048, GU/DN magnitude one.
  GU additionally requires split-K=1. Both stay within a lane AND one expert.
  Gemma geometry, prefill, palette seven, partial N and non-native paths retain
  their previous operations. The original single-panel kernel is unchanged.

Exactness and spill control
  One activation-table vector feeds two adjacent native weight panels.
  The signed halfword sums combine at most 24 u8 ternary products, bounded by
  +/-6120, before exact int32 accumulation. No FP32 operation is reassociated.
  The naive implementation spilled vector registers and was rejected.
  Final paired kernel: 384-byte compiler stack frame, no hot-loop spill/reload.
  kernel-final.s paired function is identical to the simulator-tested variant.
  -fstack-usage: DN caller 896B, unchanged from DN4; GU caller 160B when enabled
  versus 168B baseline. Pair adds its 384B callee frame below the existing 32KiB
  per-worker stack allocation. No recursion/new stack arrays added in worker.

Memory
  No heap, weight-cache, VTCM, read-pool, resident-slot or preload growth.
  Paired DN writes the already allocated per-expert acc_dn: first 8KiB of the
  existing 32KiB allocation, at most 32KiB across four experts. It may newly
  touch those pages; actual peak is for parent to measure. No expert/lane
  aliases: lane range plus panel boundary guards precede the pair invocation.
  GU reuses the same acc_gu outputs that single-panel calls already populate.

Isolated simulator timing (Hexagon Tools 19.0.04, v81, --timing)
  Four alternating-order rounds, 50 calls each; all compare identical outputs.
  Shape         storage   old cycles     paired cycles    time decrease
  DN K1536 N256 cached    347058..347202   302065..302071    about 12.96%
  DN K1536 N256 VTCM      347068..347071   302390..302391    about 12.87%
  GU K2048 N384 cached    698758..698903   638359..638362    about 8.65%
  GU K2048 N384 VTCM      698772..698779   638365..638368    about 8.64%
  Values above omit each group's cold first round; all four are in the log.
  Actual simulator VTCM address is obtained from __rdcfg(__vtcm_base), not a
  hardcoded address. Its input footprint is under 256KiB per measurement.
  This is one worker with no DMA or other-lane contention, NOT silicon/model
  TPS. Functional-mode reductions were only about 2.6% DN / 1.7% GU, showing
  why memory timing matters. Cached/VTCM agreement in this setup does not
  establish device L2 behavior. Existing ~32ms/token exposed direct-I/O wait
  remains outside this change, so this alone cannot close the gap to 25TPS.
