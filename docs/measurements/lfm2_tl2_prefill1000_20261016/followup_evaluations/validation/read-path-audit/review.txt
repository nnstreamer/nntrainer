Partial-completion calculation: feasible, limited time budget
hmx/hexkl_graph.c:180 graph_moe_miss already posts first, computes resident
experts into g->moe_rows while the ARM reads, then waits for ALL misses,
computes missing rows, and combines weighted rows in ascending expert order.
Existing hit compute is already hidden (about4ms/token). Its gain must not be
counted a second time when estimating a partial-ready design.

For k missing experts with completion times r1<=...<=rk, resident work ending
at H, and early expert computation C1...C(k-1), the optimistic additional gain
is bounded by min(max(0,rk-max(H,r1)), sum(C1...C(k-1))). Scheduling gaps,
metadata rebind, smaller batches, extra quantization/pool dispatch subtract
from this bound. No existing decode trace records r1...rk, so a measured
first-to-last completion gap cannot be extracted from aggregate profiles.

Counts give a stronger work limit than pretending all30ms is removable:
38*64=2432 layer executions; 67.89 calls/token resolves to4345 kernel calls.
With the native ROWS_OUT schedule, mixed resident/miss rounds=4345-2432=1913,
and all-four-missing rounds=2059-1913=146 (2.28/token). This inference assumes
the current native ROWS_OUT support, without per-expert unsupported fallback.
Across every round there are at most4044-2059=1985 early-arrival experts,
or31.02/token, whose work could precede the final read completion.
A UNIFORM-COST estimate from MoE net9.504ms/152 experts gives ~1.94ms/token;
a single four-miss round permits at most three early experts, ~188us on that
same model. This is a cost model, not a measured or rigorous time ceiling:
per-expert costs vary and graph/kernel fixed costs cannot simply be divided.
With unchanged I/O completion times, the rigorous compute-overlap ceiling is
the remaining missed-expert compute component, bounded loosely by the whole
9.5ms MoE net. Actual useful overlap
needs completion-gap counters and is expected below the uniform estimate
when splitting loses the current batch efficiencies.

Possible implementation boundary, NOT implemented
The current 32KiB g->moe_rows at top4/N2048 already stores each weighted expert
result independently. A partial-ready consumer can retain each result in its
original row and perform the SAME final ascending sum, without new heap/VTCM.
Each pending StagedExpert and its slot remains owned until read completion;
a claimed speculative slot moves exactly once. All evictions must be applied
once before any partial rebind. Only the DSP compute thread may rebind between
kernel calls, because metadata rebind shares the compute DMA ring. Read worker
threads must not launch concurrent registration RPCs.
Need: bounded per-load readiness + final completion/error in mailbox protocol,
readiness callback/try-consume for demanded and claimed reads, DSP wait_some,
error draining/harvest of partial successes, original-position output rows.
Both ARM and DSP must be versioned/gated together; partial records need cache
line isolation from DSP-written handle acknowledgments. Existing 1024B answer
uses860B (16 experts), leaving164B, but layout/coherency design must be proven;
no assumption of freely sharing dirty ARM/DSP cache lines. Can retain current
protocol entirely for Gemma and older skeletons. EOF after earlier successes
must still abort token and drain/return every slot before reuse. This is a
protocol change, not a local immediate-register switch. Not implemented.

Speculation: queued cancellations versus already-started I/O
Three runs: submitted3859-3860, completed3303-3335, used2780-2798,
handoff321-338, failed/cancelled0. Demand physical reads=4044-used, so each
needed miss is read once: e.g.2780 used +1264 demand =4044 exactly.
200-218 wrong queued guesses/run already expire without any physical read.
321-338 handed-off queued guesses also do no speculative I/O; their needed
read runs in the existing demand pool. Handoff mostly removes scheduling
wait, not one additional necessary payload.
523-542 completed pairs/run are never used:8.17-8.47/token,
16.48-17.08MB/token,11.45%-11.82% of all physical full-pair reads.
Current native pair callback ignores cancellation once it starts one blocking
pread; it cannot cancel that syscall. Expiry retires the slot and does not
reuse it while the worker writes. Completed but wrong reads are discarded.
No claim that all of these were still in-flight when the real route arrived:
aggregate counters also include already-ready wrong guesses.

One small bounded candidate: after a speculative pread completes, consult
its cancellation check BEFORE scattering payload/metadata, and return
Cancelled if retired. This preserves claimed/owned-slot semantics and skips
CPU copy/validation on obsolete pairs, but saves NO bytes of the completed
pread. It helps only wrong pairs that expire before copy starts. Using the
prefill's122us average copy as a cost reference, skipping every unused pair
would save roughly1.0ms reader-CPU time/token; actual eligible subset and
critical-path time are smaller and are not measured by current decode logs.
The current queued expiry already removes unread wrong jobs; moving it20us
earlier during poolAnswer has a small window and cannot erase30ms of waits.
No code/experimental expansion was made.
