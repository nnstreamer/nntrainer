Prioritized candidates, not yet production implementations
1. Measure generic affine FC readout before considering an i24 consumer.
The signed-int4 raw K2048 u8 dot lies in[-4177920,3655680], inside signed24. Existing hexkl_acc_i24 supports three planes with3KiB config in otherwise unused VTCM; it still requires runtime base0/row_stride32 and non-overlapping free-space guards. The current row-major affine consumer is int32-only. Existing i24 GLU/scatter consumers are not drop-in substitutes. A correct port would reconstruct int32, then preserve the current integer affine correction BEFORE float conversion, followed by the existing zero-point/scale/bias order and per-row post callbacks. Raw affine-corrected sums must never be truncated to24bits.
At148480 tiles, one fewer2KiB convert plane corresponds to304087040bytes=290MiB of convert output. This is an exact internal byte-count difference, not measured DRAM traffic, elapsed time, or speedup. The current readout may synchronize prior HMX work; its entire measured duration cannot be removed. No safe absolute saving or TPS estimate is available yet. No i24 port has been implemented.
2. Lower-priority affine input-sum fusion, also unimplemented.
The generic FC already fuses min/max (and optional pre-norm) with AH packing. It then rereads the packed u8 activation with a separate affine_sums worker-pool job (dma.c:909-912; hexkl_wh_affine_sums). The quantizer already has each final packed vector in a register (hvx_quant_u8.c:quant_pack_group4). Exact integer sums could potentially be accumulated there into the EXISTING per-call affine_sums array, avoiding80 extra pool jobs and80*1024*2048=160MiB of VTCM reads for this prompt. This needs measurement of sums_t and v81 register/spill analysis; a new global common-quant slow path is not justified. No new buffer/cache is proposed, and no time or TPS saving is claimed.
