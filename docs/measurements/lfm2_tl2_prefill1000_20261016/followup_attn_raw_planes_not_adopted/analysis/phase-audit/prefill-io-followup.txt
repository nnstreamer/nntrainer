Unmeasured inactive-expert hypothesis, NOT a recommendation

lfm2_moe_layer.cpp creates `active` from nonempty assignments at 1434, but queues
all missing experts in a future layer at 1626 and waits/registers the complete
due batch at 1580 before stage(active). Thus prefetch can load experts that this
prompt never routes to. A separate older compact-call diagnostic had 2283 active
expert entries out of 38*64=2432. This is not the active set of the new stage run,
nor the number of physically cancellable reads.

The inactive set becomes known only after that layer's router/top-k. Reads
already completed or in progress cannot be saved. Cancelling unstarted entries
would require new per-entry queue/slot retirement and error ownership, would
change the got-vector's acquire/LRFU score/clock/residency transitions, and could
move cost into decode. Skipping the whole-batch wait only for inactive entries
has similar lifetime and registration-order implications. Preserve this as an
unmeasured idea, not a small exact-order optimization or a predicted TPS gain.

One smaller real repeated operation exists: prefetchReaderLoop:9443-9447 calls
prefetch_done_cv_.notify_all after every expert, although the only waiter
(:4887) asks for a complete batch. In the older 2304-read/65-batch stream this
means 2304 notification calls for at most 65 terminal transitions. An eventual
completion-only notification would still need the shared-mutex predicate and
final-error completion intact. No cost/wakeup count is measured, many calls have
no waiter, and this is not proposed as a solution to the 130-ms wait difference.
No patch or new experiment is prepared.

Actual native file ranges: already coalesced, do not repeat

htp_tl2_opts.h gives native bytes = ceil(K/24)*ceil(N/128)*640.
For K2048/I1536/N2048 one expert is:
  GU codes1,320,960 + scales/colsum24,576 = 1,345,536 bytes;
  DN codes655,360 + scales/colsum16,384 = 671,744 bytes;
  contiguous GU+DN/file-next-expert stride = 2,017,280 bytes.
The file has these adjacent expert records, not separate distant GU/DN arrays.
The arena adds GU page padding: GU stride1,347,584, DN stride671,744.

canReadExpertTogether:8833 verifies DN-GU offset exactly1,345,536, native type,
PAGE0, legal shapes and fit in the existing 2-MiB direct window. readExpertTogether
:8852 supplies four destination slices (GU codes/tail, DN codes/tail) to one
weightPreadScatter, then validates/converts the small tails. No extra full expert
copy is introduced. At 9431 native LFM prefill selects this path; the accepted
decode-pair option similarly covers speculative reads, and native demand reads
already use the combined range.
