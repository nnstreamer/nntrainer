not the whole app method. References: causal_lm.cpp 697 / 2285;

The app prologue retains the same seven save instructions. The local SP

not extra64B allocation, zeroing or a new decode memory copy. Common app code

change. Indirect layout/cache effects cannot be ruled out from static code.

1024 full helper
Source arithmetic is unchanged but its compiled form is not identical. The
old helper was inlined into the app. The new shared full/range helper is an
outlined192B frame. The independently inspected row callback grows236->252B:
row setup28->32 instructions (two scalar loads,sub,mul), then the same30-
instruction hot loop repeated512 times per2048-channel row. The only hot-loop
encoding difference is a closure field offset0x20->0x28; no loop stack spills.
This is122880 additional scalar setup instructions over30*1024 rows, not a
cycle or latency measurement. The postgate callback allocation changes48->56B
in the actual NDK object. No quantitative cause of the normal0.81% PF decrease
is proven. Independent detail/hash recorded in validation.json.

Bounded isolation if parent elects a new candidate
Restore the baseline six-argument full helper verbatim, including its lambda;
put the current range-aware implementation in a separate eight-argument helper
used only by2048 chunk path. Keep identical precise-FP pragmas. This avoids
routing1024 through a generalized helper. Optionally prevent the large2048-
only chunk helper from inlining with a compiler-guarded noinline attribute,
keeping its vector metadata and loop out of the common app body. New call is
once per2048 conv layer,not per row. No public API,tensor allocation,staging

restoring a source helper alone does not guarantee whole-function layout.
