Independent review of partial-ready native LFM decode, production v2
Result: no unresolved code blocker found. This is a source/host-protocol result, not a device parity or performance approval.
Patch SHA256 7fab14b4129485bccbc35c11288d1ef16b3315e64cac9b01592e66744e636807. Base 03d652fc0.

Publication and cache ownership:
- The 768-byte optional record reuses retired mailbox bytes [128,896), after TOKEN_DONE [0,128) and before MISS_REQ at 17152. Header, progress and each load are independently 128-byte sized/aligned through the page mapping. No existing request/answer/hint offset or mailbox allocation grows.
- Header/slot bodies are immutable after their release sequence publication. ready_mask is a cumulative local OR under handle_mutex_, followed by release-store to the shared progress word; multiple demand lanes do not perform unsynchronized read-modify-write. The DSP refreshes each record before acquire loads, then reads its body. DSP code never writes the partial records, so its flush-invalidate cannot overwrite newer ARM record data from a dirty partial cache line.
- poolArm offers/clears partial records only while the server/DSP are idle. poolAnswer starts the next round only after DSP posted that next request, which follows the prior final wait. Load records and payload slots are not recycled while a DSP partial kernel can still use them.

Readers, cancellation and ownership:
- Every miss slot is staged before dispatch. readMissesReady uses the existing demand pool and existing prediction workers. The fast path requires the same configured demand lanes to cover all pending misses; no new reader count, expert slot or preload is introduced. ThreadManager compute worker count is initialized once.
- Each demand lane owns one StagedExpert. takeClaimed serializes fixed prefetch slot metadata and consumes a distinct claimed key. Its queue mutex is released before the ready callback takes handle_mutex_. There is one logical pool-server owner; per-key consumption is delegated to joined lanes. No queue/handle mutex inversion was found.
- Read failure, failed claim, callback exception and pool construction failure propagate to a final error answer only after HtpExpertReadPool::run joins every outstanding callback. Queued/reading claims stay owned until consume/drain. poolDisarm waits for server idle and predictor/prefetch drain before harvesting or releasing slots.
- Graph code always calls final wait after any ready/bind/compute failure. Error final answers clear already-bound partial entries; any stale/timeout/compute failure fails the token, and the ARM marks the queue broken, so a partially computed token is not reused as success. Timeouts remain bounded failure handling, not proof that a hung external I/O has completed. The ARM still joins its readers before releasing ownership.

DSP ordering and arithmetic:
- Resident work completes before ready rebinding. No host registration RPC or concurrent DSP table mutation is added: ready binds run on the same token thread. Evictions are applied before the first partial bind and skipped in final wait; returned handles are harvested exactly once.
- Ready runs write original missing-expert row positions with the matching weight pointer. Remaining runs execute after the final answer. The final FP32 scale/add loop still walks original ascending expert order. Existing M1 GEMV/ROWS_OUT kernels are unchanged. Actual grouped-versus-split TL2 arithmetic and hardware cache visibility must be checked on the device because the host fixture uses a MoE kernel stand-in.

Compatibility and guarded scope:
- Default is off. Both ARM offer and DSP request-tail V1 must match, with native TL2 LFM K2048/inter1536/N2048, 2..4 misses, PAGE0, demand-pool enabled, enough existing lanes and adjacent compact-readable pairs. Unsupported/one-miss/Gemma paths retain whole-answer scheduling.
- New ARM + old DSP: request-tail capability is cleared before each token and the old DSP never writes V1, so no partial records are consumed. Old ARM + new DSP: the existing mailbox initialization zeros the retired area, so no matching offer exists. Request tail extension leaves all prior fields and offsets intact. Offer reset covers sequence-wrap stale partial records.
- v2 initializes env->miss.ready=NULL in nntr_hvx_graph_env. Other production environment creation goes through this helper or copies the token-owned environment. The added internal function pointer requires a coherent full DSP rebuild; do not mix object files using old/new hexkl_graph_env layouts. It is not a new FastRPC method or ARM public ABI.
- No new Linux-only production API was added. Header atomics have GCC/Clang and MSVC branches. The pthread/O_DIRECT test runner explicitly skips non-Linux.
- Common token entry still clears 768 bytes and refreshes the offer line even when opt-in is off; no claim of literally zero Gemma plumbing overhead is made. Gemma MoE arithmetic/scheduling is unchanged.

Memory and validation:
- No new persistent expert/activation cache, no extra VTCM and no mailbox capacity increase. ARM adds an 8-byte statistic and bounded callback/header temporaries. Compiler stack reports supplied by author: hexkl_token_main 184->408 bytes (+224), graph_moe_miss 496->504 (+8); new ready callback 136 and ready-row helper 88 bytes. These are small call-stack changes, not weight-cache growth.
- Independent ASan/UBSan: actual token callbacks + complete graph object, 103 lifecycle/order/error cases PASS; actual extracted readMissesReady/adoptPrefetch plus real WeightFileReader/O_DIRECT/read pool/prefetch, 84 cases PASS. All three intentional mutations were rejected with diagnostics. Commands and logs are under checks/ and exact source hashes/reproduction argv in validation.json.
- The ARM fixture extracts scheduler/adoption helpers, not complete poolAnswer/poolArm/poolDisarm. Their publication, lock and lifecycle anchoring was reviewed directly above. Host cache operations are fences and the arithmetic is a stand-in. No device, root tree or author source was changed during review.
