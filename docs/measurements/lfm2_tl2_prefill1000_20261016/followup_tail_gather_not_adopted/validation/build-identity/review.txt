DSP rebuild identity investigation and tail A/B limitation, 2026-10-17

Same-source code generation is not byte reproducible in the current Hexagon compiler invocation. No source change is required to produce the observed probe_lane and softmax variants. The tail experiment remains NOT ADOPTED: neither a causal gain nor a causal regression is established by its 12-run matrix.

Control and rebuilt are each 738992 file bytes, but .text is 598360 vs 598328. Their only changed function sizes are probe_lane 5320->5288, hvx_softmax_q 4156->4152, and hvx_softmax_q16_part_max 1216->1220. Equal function size does not imply equal instructions.

The independent test compiled unchanged source with the same argv, cwd, compiler binary and output path four times per TU. probe_lane sizes were 5320/5256/5288/5288; softmax q/part_max sizes were 4152+1220, then 4156+1216 three times. Distinct object SHA256s and exact command arrays are in recompile/results.json and commands.json. After screening relocation-dependent operands, the compiled variants reproduce the control, rebuilt and candidate probe instruction streams, and both softmax streams. The source snapshots and hashes, compiler version/hash, and comparison against recorded f7b16e48 base are retained in input-source-hashes.json; all seven inspected tracked source files exactly equal that commit. This establishes observed compiler output variability, without diagnosing its internal random seed or claiming all source-equivalent builds vary.

MoE baseline a19d1ee9 and ring baseline7751082a were separately compiled three times each with a fixed path/argv. Each set was byte-identical (MoE487a17f3..., ring96ece1d9...). These six bounded checks found no variability in those two TUs; they do not prove universal determinism, nor cover every future candidate. No new MoE/ring code was written.

Frozen tail candidate vs measured control:
The expected changes include main MoE and the new moe_lfm_pack_bg_worker. Unrelated register allocation or instruction-order changes also appear in probe_lane; hvx_softmax_q; hvx_attn_m1_f32.c's append_head_q8_vector, head_pipeline_scores and run_p1; and generic router rows_block_4x3/rows_block_4x4. Those last functions retain their sizes but not their instruction streams. moe_expand_submit additionally differs in loop-end/nop packet placement after layout changes. CRT PC-relative values, GOT slot offsets and normal call relocations move as well. Thus the source patch is single-topic, but the two whole DSP binaries do not isolate only that topic's machine-code change. The magnitude of any confounding performance effect is unknown; the three-pair model result cannot assign a gain or a regression to tail gather alone.

The comparison script is an explicit screening aid: it symbolizes known GOT offsets, drops relocation extension/nop/packet decoration, and normalizes branch targets. It is NOT a semantic-equivalence proof. Exact binaries, disassembly and hashes remain in this temporary evidence directory; the compact archive stores hashes, commands and focused exact disassembly slices, not the large full listings. The 57 changed .rodata bytes fall in relative target-table regions and are consistent with changed code layout; this is not evidence of model-weight or quantization changes.

A separate audit-tool side effect occurred after the original mismatch was observed: llvm-objcopy --dump-section without an explicit output rewrote its input ELF. Root recovered exact control3badd and rebuilt720835 from unchanged device copies, preserving the rewritten files and the incident record. No model ran with the rewritten files. All comparisons above use the explicitly suffixed recovered original copies. The side effect did NOT cause the initially observed .text size difference. The final selected runtime restores the immutable original control3badd, not the byte-different full rebuild; root-normal-restored.json binds all seven selected original runtime hashes. No device access or root edits were performed by this reviewer.

For future DSP A/B, preserve one baseline object set and recompile/link only the changed translation units, retaining input/object/runtime hashes. Check unchanged objects byte-for-byte, and keep the same compiler settings and build inputs. This bounds unrelated whole-build variability; it still does not make the modified TU's code generation deterministic.
