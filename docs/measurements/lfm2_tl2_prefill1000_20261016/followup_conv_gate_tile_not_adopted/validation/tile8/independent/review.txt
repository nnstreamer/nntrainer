Ownership, arbitrary execution order, and halo proof
  Each tile owns exactly8 distinct output rows. It uses immutable projection
  rows to recompute the two halo gates at interior tile boundaries. Therefore
  reversed, shuffled, or stolen tasks do not depend on another concurrent tile
  writing GATED. At the one RPC boundary1920, the first tile reads only saved
  GATED rows1918/1919. They were completed before the prior parallel_for joined
  and before the next RPC could invalidate its projection. Only1918/1919 and
  2046/2047 are written for M2048; only1022/1023 for M1024. Other GATED rows are
  intentionally untouched and can remain poisoned. The direct helper has no
  global progress state and makes no nested parallel_for call.

  ThreadManager's real scheduler has one owner per index via range_length and
  range_end atomics. It waits all workers and applies an acquire fence before
  parallel_for returns. Captured argument references stay alive through that
  join. task_ can retain a completed callback until the next dispatch, as before;
  it does not execute the stale references after the join. No asynchronous
  projection view escapes its RPC chunk. The existing sync fallback and the
  pre-work input/workspace/state alias checks remain in force. The later
  projection/CPU errors propagate without a new false-return retry. State is
  saved only after all chunks succeed, with the old out-projection ordering.

FP32/order evidence
  Each output preserves pre-gate FP32 multiply, cur*w0, FMA(prev1,w1),
  FMA(prev2,w2), and multiplication by B. The explicit vector code is inside
  the original precise-FP scope. The original scalar pregate source says A*C,
  but the actual NDK vector and scalar instructions use C then A. New cur and
  recomputed halos use that same C,A operand order, relevant to NaN payloads.
  Actual old full/range epilogue and new callback instructions retain the two
  FMAs in order; FP32 register values do not add extended-precision storage.
  Halo recomputation does add repeated multiply operations, not an arithmetic
  reduction or reordering of an output's chain. We claim output/state parity,
  not an identical total instruction/FP-operation trace.

  Tile8 only changes tile_rows16->8 and its comment from the reviewed Tile16
  algorithm. This was nevertheless rechecked on the final8 source:128 tile
  jobs at1024 and240+16 at2048, instead of64 and120+8. Baseline remains the same
  1024+1024 or1920+1920+128+128 row-job topology. Eight-row halos, final-row
  writes, and bad partial-tile guards are exercised by the final fixtures.

Timing and memory controls/limits
  All three paths share the same buffers, projection values, weights and state
  lifetime. Each has3 warmups. The six cyclic permutations balance each position
 10 times plus one additional012 order across31 repetitions. Timed regions
  include common sampledCopy plus33 memcmp checks per chunk and final state
  copy; allocation, fill, exact comparisons and optional host sweep are outside
  the timer. No per-iteration samples are printed, so paired variance or a
  confidence interval cannot be reconstructed from median/min/max alone.

  Alternation reduces order bias but does NOT equalize cache state: baseline
  writes all GATED rows while tiles write only the final rows, so a preceding
  path changes the next path's residency/dirty lines. Sweeping the existing
  host projection is not an explicit flush and cannot certify a cold or equal
  cache. Frequency/interrupt/background state is not controlled by this tool.
  ION is CPU-filled and then CPU-read; no DSP-produced data invalidation,
  projection execution, concurrent expert I/O, or full-model memory pressure
  is simulated. The initial1024 warm maxima contain large scheduling outliers.

  The production workspace layout/allocations stay unchanged. The code avoids
  writing most existing GATED rows, not allocating a smaller tensor. The tile
  lambda is56B (seven references), and the actual std::function wrapper is64B
  versus existing fullpost48/rangepost56. It replaces the existing task_, with
  the same temporary old/new coexistence and later-dispatch release contract.
  Thus no new persistent data cache exists, but zero metadata/stack cost is not
  claimed; allocator overhead is not measured by sizeof or source inspection.
  Existing2048 staging requests/capacities and48MiB copy removal are properties
  of the already-reviewed chunk-view base, not a new Tile8 improvement.
