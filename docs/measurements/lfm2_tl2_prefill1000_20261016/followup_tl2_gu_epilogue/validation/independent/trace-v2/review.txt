Protocol/source review
  Each qualified successful native LFM M1 call snapshots counters after the
  existing foreground, last-background and live expansion-slot joins. The
  counter workers update four relaxed atomic uint32 values. The existing pool
  join supplies completion; no concurrent writer remains while snapshots are
  taken. Serialized kernel calls are an explicit precondition, also required
  by the existing global HMX/DMA state. The diagnostic does not remove joins or
  change computation. A fifth uint32 is incremented only inside the successful
  trace filter, giving one process-local sequence per log record. Sequence
  state is +4 bytes over v1, diagnostic total 20 bytes; no allocation/cache.
  Zero or wraparound sequence is rejected by the parser. This is adequate for
  a fresh process containing the bounded workload; it is not a multi-process
  or >UINT32_MAX-call tracing protocol. Errors do not consume sequence IDs.

  Matching repeated sequence+fields are transport replays, not new calls.
  Conflicting repeats fail. One PID, contiguous IDs starting at 1, fixed native
  geometry, valid lane counts, exact fused/unfused counters and the complete
  token*layer*top-k expert/tile totals are required. Reordered delivery is
  allowed and reported separately. Timestamps/TIDs are not invocation identity.
  Missing trailing records fail the expected workload total, not just sequence
  continuity. The parser is intentionally for all-native magnitude1 LFM data;
  zero fast-path counts or mixed/fallback traces are rejected, not generalized.

  Review found and author corrected a parser-only issue: materializing
  set(range(1,max_sequence+1)) could allocate billions of entries for a sparse
  uint32-valid sequence. Final parser instead checks max_sequence==unique_count,
  given keys are unique and >=1, so rejection is bounded by input size. The
  diagnostic source and production patch did not change for that correction.
