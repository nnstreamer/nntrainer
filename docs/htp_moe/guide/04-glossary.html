4. Glossary — every acronym and term on these pages

definitions as used in plans 85, 88, 90, 100, 101, 105, 113 and 117, docs/measurements/88-moe-call-marshalling.md, 100-dma-chunk-list.md, 117-m1-gemv-vtcm-feed.md and 120-upstream-4327-sync.md (@ 7ded3ce9, on htp_moe since PR #121 merged), contract docs/plans/0001-…, LEDGER.md (the LEDGER numbers two different rules "24": the swiglu lane-time rule under #94/#101 and the subnormal rule under #95; this guide says "the first rule 24" and "the second rule 24"), BENCHMARK.md, doc 49 §3–§4 and the code under nntrainer/tensor/htp_backend/ (including PR #119's htp_graph_desc.h and hmx/hexkl_graph.c, PR #125's hvx/hvx_m1_ops_f32.c + m1_ops_det.h, PR #126's hvx/hvx_attn_m1_f32.c + attn_m1_det.h) and test/htp/ (the IDL, build.sh, host/run_host_checks.sh, host/run_inproc_e2e.sh), and docs/plans/130-per-token-wiring.md. PRs #121 and #125–#128 merged on 2026-09-27 (PR #124, a Mac container for the host gates, was merged and reverted on 2026-09-28, 0feb13cf); terms from them say "landed, unwired" where the code is in the tree but not on the decode path.

A/B
Two variants run in the same sitting on the same phone; only their ratio is a verdict (LEDGER rule 9).
acc, acc_read
The HMX accumulator (64 rows × 32 int32) and the instruction that copies it out to VTCM; the HMX stalls while it is read. Profile column acc.
adb
Android Debug Bridge: the USB tool that pushes files to the phone and runs commands on it. Agents never run it.
0x80000406 (skel does not load)
FastRPC error from remote_handle_open_domain, logcat dlerror RX VA 0xFFF00000 outside ELF segment: the DSP loader refused the skel image. On this project it meant undefined project symbols in the skel (#97); not a segment-layout bug. See page 1 §2.
AEE_EBADPARM (0x8000040E)
FastRPC's "bad parameter" error; on this project it almost always means a skel that loaded but does not match the app's IDL — a stale skel or app (rule 3). Distinct from 0x80000406 above and from [Engine] htp Context is not registered (app-side: the htp context exists only in an ENABLE_HEXKL build, engine.cpp:70–72).
AH tile
"Activation, HMX order": 64 rows × 32 k-values of u8, 2048 B, the layout of the activation operand the HMX reads.
anchor cell (DMA_REPLAY workers=1 load=0 pace=0)
One of the 11 old MoeChunkReplay cells, unchanged since #94: the traced 46-descriptor list replayed unpaced by one worker with no compute. Every handoff reads it first, cold, verbatim, as the sitting's DMA rate; an absolute mm gate on a DMA-fed path is read next to it (rules 30, 32, 34). Values: 561.5 µs / 40.2 GB/s (#94 s2), 719.6 / 31.4 (#100), 724.0 / 31.2 (#113) on R3CY205ZMND; 607.9 / 37.1 and 605.3 / 37.3 (#117, two sittings) on R3CY10WM83Y. It prints checksum_ok=n and a FAILED that are #99's known condition, not a regression.
arena / heap / hot cell
The three cells of #105's microbench MoeM1GemvFeedVsCompute: the same GEMV over weights in the ION arena, in the ordinary DSP heap, and over a set small enough to stay in the L2 cache. Hot = the arithmetic alone; arena − hot = time spent waiting for bytes.
arena (ION arena)
3840 MiB of ION memory in 256 MiB chunks, mapped once into the DSP, holding all 1408 expert weight matrices in WH order.
ARM
The phone's CPU cores (Cortex big.LITTLE), where the app and everything not on the DSP runs.
blocked wait / dry wait
A DMA wait that found its descriptor still in flight (blocked) vs one that returned at once; counted per call by the ring trace (waits=… (blocked …)).
bus vote
A request the DSP makes for DDR bandwidth (40 GB/s at session open); the novote skel drops it. Worth ≤ 4 % in #77.
c_star (the validated ceiling)
#100's replay cell that pushes the DMA probe's own per-call shape one descriptor at a time and checks the bytes it wrote afterwards (tag=N/N, checksum_ok=y). It is the fastest rate the engine is known to have delivered through a real per-call list in that run: 26.3 GB/s on 2026-09-23, 0.36× the same run's DMA_PROBE shape iii. Every absolute GB/s gate is read against it (LEDGER rule 28).
cache maintenance (clean / invalidate)
What the FastRPC driver does to a cached ION buffer on every call so the DSP sees the ARM's writes (clean = write the cache back to DDR) and the ARM sees the DSP's (invalidate = drop stale lines); it covers the whole buffer, not the bytes used. With the old 4 MiB staging pair this was 245.8 µs of every decode call (#88).
cDSP
The compute DSP domain of the Snapdragon; the FastRPC session opens with _dom=cdsp.
cold / warm call
A single-shot MoE call after the ~0.6 ms FastRPC gap (profile level 2) vs the last of five back-to-back repeats (level 3); the DMA trace is printed for both.
control (variant A)
The unchanged reference binary that opens every sitting.
conv block / causal_conv1d
LFM2's non-attention mixer: two FCs around a short depthwise convolution with two gating multiplies.
CPU control
The q40 model on the CPU: the tok/s floor the NPU must beat.
DCVS / DVFS
Dynamic clock and voltage scaling: the DSP may lower its clock when idle; a candidate cause for run-to-run drift.
decode
Generating tokens one at a time after the prompt; M = 1 everywhere.
decode graph description (op list; htp_graph_desc.h)
PR #119's description of the whole decode step as 32-bit words: a 7-word header (magic HTPG, version, layer count, op count, hidden width, vocab, max sequence), one kind word per layer (conv / attention) and per FFN (dense / MoE), then one 76-word record per op — kind, layer, the resident bit, K / N / N_out, expert count and top-k, two activation slots, next_mm (the next weight-streaming op), and 32 + 32 weight handles for a MoE op. The LFM2 builder emits 228 ops for LFM2.5-8B-A1B (11 per attention layer, 9 per conv layer with a MoE FFN, 8 for the two dense layers, 2 for the tail), 22 of them MoE; the validator returns one named AEE_* code per finding and never AEE_EBADPARM. Built by lfm2_moe_causallm.cpp, validated on the ARM before it is sent and again by the skel at graph_init.
DDR (LPDDR5X)
The phone's main memory; 34–38 GB/s measured for one reader, the speed limit of decode.
dequant / requant / quant
int32 → f32 with scales (dequant), f32 → u8 for the next matrix (requant), the first f32 → u8 of the activation row (quant).
descriptor
One DMA job: row bytes × row count at a source stride, to a VTCM address (with its own destination stride). An M=1 MoE call pushes 46 (4 experts × 11 + 2 copies).
_det spec (m1_ops_det.h, attn_m1_det.h, swiglu_det.h)
A scalar C header that fixes an operation's result bit for bit — the order of every add, an exact max, a deterministic exp_det / recip_det (so recip_det(1.0f) is 0x3F7FFFFF, not 1.0f) — so that the HVX kernel, the host check on hvx_emu/ and the device gtest can all be memcmp'd against it. The CPU path runs no _det, which is why bit-identical NPU-vs-CPU text is impossible once these ops leave the CPU — hence the 2026-09-28 accuracy column: text y/n + NNTR_PPL + user text approval; a CPU NEON _det twin was not taken.
descriptor list (chunk list)
The ordered 46 descriptors and 30 wait points one M=1 MoE call on the HMX path issues on the ring, over 32 arena regions; recorded by the DMA ring trace and replayed by MoeChunkReplay. Row h of #94 read this list as slow on its own (40 GB/s vs a 107 GB/s probe); #100 showed it runs at 1.19× the validated ceiling c_star, i.e. faster than any checked per-call rate — there is no list-side loss (rule 19 withdrawn, rule 28). Off the decode path since the GEMV default (2 descriptors per call).
DMA
Direct memory access: the DSP's copy engine, driven by descriptors (2D: row bytes, stride, row count) through a ring; how weights get from DDR to VTCM.
DMA ring trace ([HTP-DMA], DMA ring:)
PR #93's bookkeeping of every push and wait on the ring inside a timed MoE call, read back through moe_dma_trace_read and printed by the ARM; off unless NNTR_HTP_PROFILE ≥ 2.
dma_replay / MoeChunkReplay
A skel entry and device gtest that push the M=1 call's descriptor schedule with no compute in between, to time the engine on the in-situ list alone; 11 old cells (workers × pacing × competitor × fresh pages × gap), whose content check fails because they write VTCM packed instead of strided (#99; the timings stand), plus, since PR #112, the 16 DMA_REPLAY_X cells below.
DMA_REPLAY_X (the #100 replay cells)
Sixteen descriptor lists built on the host (test/htp/nntr_moe_dma_plan.h, nntr_moe_dma_cell) and replayed one worker, unpaced, 20 calls each, every one checked by a tag sum over its VTCM windows: the traced list as-is / over fresh regions / without waits / gate-up only / down only; the probe's shape iii chained / one dmstart per descriptor / linked one at a time / written strided; c_star; and the feed candidates f1–f3 with and without an HVX job streaming VTCM (load=0 / load=2). All 16 passed in #100 and all read 26–32 GB/s (plan 100 §3.2; 100-dma-chunk-list.md gtest table).
DMA_PROBE / DmaProbeShapes
The isolated arena-rate gtest (16 lines: four shapes × workers 1–4). Shape iii = 8 KiB × 64 rows @ 56 KiB stride is the gate/up chunk geometry; 106.9 GB/s cool / 88.8 hot in #94 (rule 18), 73.2 in #100. Not a ceiling: no checked per-call path reproduces it (rule 28); its one-worker rows also drift 15–30 % between sittings (rule 30).
drain
Profile column: time spent waiting for a DMA transfer that was not hidden behind compute.
DSP
Digital signal processor; here the Hexagon core inside the HTP.
dspqueue
Hexagon SDK's low-latency ARM↔DSP queue; deferred alternative to plain FastRPC calls.
engine GB/s (in situ; the DMA ring: bracket)
The rate the DMA engine actually moved bytes while it was busy inside a layer call, printed as busy=lo..hi us -> engine lo..hi GB/s: a range, because completion is observed only at the next instrumentation point. Under the VTCM feed #117 read 32.3..34.4 with busy 640–682 of a 712 µs call (the engine never idled; gate ≥ 28 on the lower bound); the weight DMA: line's "averaged over the call" divides by dsp and under-reads it (≈ 31). The gap to the same sitting's anchor (37.3) and vtcm microbench (37.7) is ㉓, ≈ 86 µs per call; #120 A read the same bracket (32.3..34.4) as a sitting's control, so the gap stands on this unit.
expert
One of 32 small FFNs in a MoE layer: gate_up [2048 × 3584] and down [1792 × 2048], 5.25 MiB in int4.
FARF
The Hexagon SDK's DSP-side log macro (HAP_farf.h); lines at HIGH are silent unless the log mask enables them, ERROR lines reach logcat. PR #119's forward prints one per call: [graph] start= resume= ops= pcyc= moe=.
FastRPC
Qualcomm's remote procedure call from ARM to DSP; one call = marshal arguments, wake a DSP thread, run the skel function, return.
FC (fully_connected)
A dense matrix multiply layer (in_proj, out_proj, q/k/v/o, dense FFN).
feed (weight feed, VTCM feed)
How the weight bytes reach the unit that multiplies them. The GEMV first read the arena in DDR directly (21–27 GB/s), and #105 showed the wait is DDR latency (rule 26). A VTCM feed — DMA each expert's weights into VTCM while the vector unit computes — was measured by #100 at 31.6 GB/s beside HVX (demoted, cycle 11), re-filed by #113 as a rate lever at ≈ 1.33× once the anchor cell fixed that unit's DMA bound at 31 GB/s (cycle 12), and built and measured by #117 (2026-09-23, second unit): whole-matrix descriptors (the f2 shape), two 3.5 MiB VTCM slabs that alternate by expert, one expert ahead, the l2fetch lead off. M==1 mm 932 → 676 µs (gate ≤ 760 passed twice), engine 32–34 GB/s inside the call, transport 190 → 92 µs, decode +29–32 % with identical text 36/36. The default since PR #118 (HVX_GEMV_M1_FEED 1u, merged d79c0efe); its win is unit-dependent (rule 34).
feed=vtcm / feed=arena; applied=0x303e1 / 0x103e1 / 0xe1
The banner's name for the feed cell a run asked for and the moe_set_opts word the DSP echoed. Bit 5 says bit 17 is authoritative; bit 17 = 1 is the VTCM feed. An unset run since PR #118: [HTP] moe m1 gemv: on (applied=0x303e1) lead=192KB rows1=1 feed=vtcm source=default; NNTR_MOE_HTP_GEMV_FEED=0: 0x103e1 … feed=arena (the D192 arena read, #117's A); LEAD_KB=0 ROWS1=0 FEED=0: 0xe1 (the pre-#115 cell). feed=default was the pre-flip wording for "the skel's build value" and no longer prints; an A log showing it, or feed=arena, is the pre-flip default and voids the sitting (rule 21). Per call, the level-2 M==1 row's feed=n/calls is the proof (htp_moe_opts.h, htp_compute_ops.cpp banner).
feed shapes f1 / f2 / f3
#100's three DMA candidates for a VTCM feed, per expert: f1 six contiguous 1 MiB-class pieces, depth 2 (hvx_impl's mm_pf_kick shape); f2 two whole-matrix descriptors (gate_up 57 344 × 64, down 32 768 × 56), the best at 31.7 / 31.6 GB/s; f3 the probe-iii columns written strided so the GEMV can read them. load=2 = an HVX job streams VTCM at the same time; it costs 0.1–0.3 % (rule 29). f2 is #117's list: each descriptor is one contiguous copy (destination stride = source stride = row size), 8 per call, depth 2 — the push moe_push_weight_chunk already issues when a column is as wide as the matrix (plan 117 §0).
FFN
Feed-forward network: the gate/up → SwiGLU → down block of a layer; MoE or dense.
GEMM / GEMV
General matrix–matrix / matrix–vector multiply. Decode is GEMV (M = 1).
first expert ready (µs)
On the DMA ring: line, when the first expert's weights were resident in VTCM: the part of the feed no compute can hide, because there is nothing to compute yet. Under #117's feed 121–122 µs (the first 3.5 MB slab at ≈ 33 GB/s); on the old HMX path 151–165 µs (the un-hidden first expert, attribution row f). The first candidate for ㉓: kick expert 0's slab before the activation quant, the call's first ≈ 20 µs.
forward entry (one call per token; NNTR_HTP_FORWARD=1)
Plan 85's skeleton for ⑨, merged as PR #119 (b4c96bdb, 2026-09-23; #85 closed): the IDL entries graph_init / graph_release / forward / forward_debug, the decode graph description, and a DSP-side op table with MOE as its only resident kind. NNTR_HTP_FORWARD=1 (default off) routes decode's MoE calls through it; each call still runs one op, so it is 22 calls per token — 0 ms by construction, no sitting has run it. It saves time only once every op between two MoE ops is resident: #82's small ops (PR #125) and #81's attention (PR #126) landed on 2026-09-27 but are not in the table — #130 wires them, and plan 130 counts 95 calls per token with only those five, because the FCs, ADDs and the router still cut every stretch off from the MoE op — and beyond them the Q4_0 FC projections, the router and the tail (LEDGER's second ㉓ row). The main lever now: 12.1 of the 27.8 ms per token are transport and CPU work outside the MoE call (cycle 16).
wiring (#130)
The issue that puts the landed M=1 kernels (#82's RMSNORM / QK_NORM / ROPE / CONV1D_GATE, #81's ATTN_M1) into hexkl_graph.c's kernel table behind NNTR_HTP_FORWARD, seeds the KV cache after the CPU prefill and uploads the RoPE table at graph_init; host-gated by graph_host_check and run_inproc_e2e.sh. Plan 130 (committed 39af2f39, 2026-09-28) counts 95 FastRPC calls per token with all five kinds on — more than today's 22, ≈ −20 % decode expected — so it is the proof of the resident set, not a gain; the count drops only with the follow-up resident set (M=1 FCs, router, lm_head). Its device handoff is read under the accuracy column the user decided on 2026-09-28: text identical to the CPU q40 run (y/n) and NNTR_PPL vs the CPU q40 PPL, plus text approved: y/n by the user per variant (differing text is not a fail by itself, an unapproved text is not a pass, a PPL regression fails on its own).
FWHT / Hadamard rotation
Fast Walsh–Hadamard transform: an orthogonal ±1 butterfly that spreads a vector's values evenly; #95 plans a 256-point one before the down-projection requant, with the inverse folded into the weights offline.
gather / scatter
Gather: bring a block's activation rows (and scale/zp) to where the HMX reads; scatter: out[row] += weight · result, the weighted sum of the experts.
gen (G)
Generation length in tokens: 64 / 512 / 1024 in every handoff.
generation(last 64) (#89) — PR #128, merged 2026-09-27
The decode tok/s over the last 64 completed tokens that contract §1.1 asks for beside the whole-generation figure, printed by the base report block as generation(last 64): 64 tokens, <ms> ms, <tok/s> TPS (with fewer than 64 tokens the window is the whole generation and the line says so). Host-proven on the tiny fixture; not yet in any device log, so every "last 64" cell on page 3 is still n/a (causal_lm.cpp:735–748).
graph_init / graph_release / forward / forward_debug
The four IDL entries of the per-token path (PR #119, after moe_set_opts in nntr_hvx.idl). graph_init takes the decode graph description, validates it, binds its weight handles against the session's table and keeps it (a second init without a release is AEE_EBADSTATE; a handle a resident op names cannot be released while the graph lives); forward(start_op, pos, row_index, row_count, row_weight, act_in → act_out, resume_at) runs ops from start_op while they are resident and returns where it stopped; forward_debug is the same with at most n_ops_limit ops plus per-op pcycles and the MoE stage table (used under NNTR_HTP_PROFILE ≥ 2). 0x8000040E from any of them = a skel built before PR #119.
graph_host_check
The host gate PR #119 added to run_host_checks.sh: GRAPH VALIDATOR OK: LFM2.5-8B-A1B n_ops=228 moe=22 … plus a table of mutations each failing with its own code, GRAPH FORWARD IDENTITY OK (22 start ops, no op resident), GRAPH FORWARD BIT-IDENTICAL: MoE op vs direct layer_run …, GRAPH FORWARD REFUSALS OK, GRAPH CHECKS PASS.
greedy decoding
do_sample: false; the argmax token every step, so runs are repeatable.
handoff
A measurement document (docs/measurements/<issue>-<slug>.md) the user runs on the phone in one sitting and fills in. Its binaries must be rebuildable from the named commits on any workstation; a staging path is not a deliverable (LEDGER rule 22).
HexKL
Qualcomm's kernel library exposing the HMX (libhexkl_micro.a on the DSP, libsdkl.so on the ARM).
HMX
Hexagon Matrix eXtension: the matrix unit; one instruction multiplies a 64 × 32 u8 tile by a 32 × 32 i4 tile into the accumulator.
host / dsp / transport
Profile columns: host = the call as timed by the ARM; dsp = as timed by the DSP; transport = host − dsp, the round trip. In one sitting on one binary (#100): 185.8 µs per decode call on the GEMV path vs 84.6 on the HMX path, the +101 being the GEMV path's own cost, paid back 3.4× in dsp (1041.5 vs 1384.6). Transport and host drift between sittings like tok/s (401 vs 649 µs on identical sources two hours apart), so they are compared only as an A/B inside one sitting; only dsp (and mm) is comparable across sittings (LEDGER rules 20, 23; ⑦).
HTP
Hexagon Tensor Processor: Qualcomm's name for the NPU (DSP + HVX + HMX + VTCM).
HVX
Hexagon Vector eXtensions: the DSP's 1024-bit SIMD unit; a thread must own an HVX context to use it. The session sizes its worker pool from the context count qurt_hvx_get_units() reports (6 lanes on v79 per plan 105; older text said four).
hvx_emu/ (test/htp/host/hvx_emu/) — PR #125, merged 2026-09-27
An intrinsic emulation — one IEEE f32 operation per lane — under which the real HVX sources compile on the workstation. run_host_checks.sh uses it for #82's small ops (M1 OPS BIT-IDENTICAL against m1_ops_det.h) and for #81's attention with the real worker pool on pthreads (ATTN M1 BIT-IDENTICAL against attn_m1_det.h); the in-process build uses it for the f32 intrinsics. Distinct from libnative, the SDK's own emulation the GEMV check uses.
IDL / qaic / stub / skel
The interface file nntr_hvx.idl; the generator; the ARM-side caller code; the DSP-side receiver library libnntr_hvx_skel.so.
issue-bound / feed-bound
Whether a loop is limited by how fast the core can issue its instructions or by how fast the data (here the arena weights) arrives; #105's microbench MoeM1GemvFeedVsCompute told them apart for the GEMV: at m = 1 over the arena it is feed-bound, ≈ 74 % of mm under the one-row loop (LEDGER rule 26).
int4 (i4) / u8 / int32 / f32
4-bit signed weights; 8-bit unsigned activations; 32-bit integer sums; 32-bit floats.
in-process host E2E (-Dhtp-inproc=true, build_htp_host/, NNTR_HTP_DUMP, run_inproc_e2e.sh) — PR #127, merged 2026-09-27
#84's harness: a second meson build in which the DSP skel sources are linked into libnntrainer.so in place of the FastRPC stub, on scalar stand-ins for the HMX tile / GEMV / quant and hvx_emu/ for the f32 intrinsics, so the tiny LFM2-MoE fixture runs a whole prefill + decode through nntrainer's own loop on the host; the gate prints five E2E lines and INPROC E2E PASS (rung 1 of the gates since PR #127). NNTR_HTP_DUMP=<dir> makes any run, host or phone, write every MoE call's input and output plus a manifest; tools/htp/htp_dump_eval.py compares two such directories. Host dsp= / transport columns are the stand-ins' clock and are never quoted. #130's wiring is gated here.
ION
Android's shared-memory allocator (rpcmem): buffers both ARM and DSP can map; uncached on the DSP side.
KV cache
Stored keys and values of past positions that attention reads at decode.
KV cache, DSP-resident (attn_m1_register / release / kv_append / forward) — PR #126, merged 2026-09-27
#81's cache object for decode attention on the DSP: K stored transposed per layer and kv head (Kt [layer][kv][64][max_seq], one f32 vector = 32 positions) and V row-major, f32 on the DSP heap — 48 MiB at max_seq 2048, 26 % of the ≈ 182 MiB heap — plus 256 KiB scratch, one worker-pool unit per kv head. To be seeded after the CPU prefill with the CPU's fp16-rounded k/v (the decode rows are f32). In the skel, unwired until #130.
L2 (cache)
The DSP's second-level cache, filled automatically from DDR (and by l2fetch). "L2-hot" = data already there.
l2fetch
DSP instruction that prefetches a 2D region into L2 ahead of vector loads; non-blocking, up to 3 queued per thread, lower priority than real loads.
l2fetch lead
How far ahead of use a lane prefetches its weight columns. The GEMV issued each column's l2fetch right before that column's loads (lead 0); #105 / PR #107 lets each lane fetch its next block of columns while computing the current one (HVX_GEMV_PF_LEAD_KB: 0 / 64 / 192 KB = variants B1 / B2 / B3; too long a lead could evict useful lines from L2). Measured in #105: 0 / 64 / 192 KB gave mm +7.4 / +3.3 / −4.3 % against the four-row loop, still improving at 192 KB — and only ever on the one-row loop. #113 swept it to 1536 KB on both loops (see lead matrix): it harms the four-row loop at any value (2.1–2.5×, interference with the loop's own loads, rule 31) and helps the one-row loop only to 192 KB. Read it as an ordinal, not a byte count: with three outstanding l2fetch per thread, the up half of a block gets about two column-computes of lead whatever the nominal KB. Default 192 KB with the one-row loop since PR #115 (D192).
lead matrix (#113), rows1, tune bits
The 2 × 5 grid of (inner loop: four-row gemm_rows4 or one-row gemm_row1) × (l2fetch lead 0 / 192 / 384 / 768 / 1536 KB) that #113 measures in one gtest run and four E2E variants. Both knobs are chosen at run time through spare bits of the moe_set_opts word (bit 7 "tune", bits 15:8 the lead in 64 KB units, bit 16 rows1), from NNTR_MOE_HTP_GEMV_LEAD_KB / NNTR_MOE_HTP_GEMV_ROWS1, and echoed in the banner; a skel that ignores the bits makes the app throw. The top lead is deliberately past any plausible L2 so the turning point lies inside the range (the lead saturates structurally at ≈ 2368 KB in stage A). Gate: mm ≤ 840 µs (plan 113 §1–§3). Measured 2026-09-23: arena four-row 133.5 / 282.3 / 316.4 / 323.1 / 328.4, one-row 154.3 / 129.1 / 139.4 / 147.3 / 155.2 ns_per_tile; the gate failed on every cell (minimum D192, 937.0 µs). Crossing an expert boundary with the lead is #114 (p2).
D192
#113's name for the (one-row loop, 192 KB lead) cell, applied=0x103c1: the matrix minimum, mm 937.0 µs (−6.3 % vs the four-row no-lead A), decode +4.11 / +3.29 / +4.26 % at G 64 / 512 / 1024 with byte-identical text. Missed the 840 µs gate and became the M=1 GEMV default anyway by user decision (rule 33): PR #115 (c45d4433) sets HVX_GEMV_M1_ROWS1 1u, HVX_GEMV_PF_LEAD_KB 192u. Confirmed on a second unit by #117's A vs A0 (+3.56 / +2.41 / +3.93 % warm, +2.41 / +4.16 / +3.91 % cooled) and, as #117's A, the BENCHMARK "now" until cycle 16 (28.22 / 27.89 / 27.23); since #120 the same cell is A0 (FEED=0, 28.62 at G=64, −20.4 % under the feed default). The old cell is NNTR_MOE_HTP_GEMV_LEAD_KB=0 NNTR_MOE_HTP_GEMV_ROWS1=0 (0xc1 before PR #118, 0xe1 with FEED=0 after it). Under the VTCM feed the lead is forced off, so D192 reads as (one-row, ignored).
interference vs eviction (prefetch)
Two ways a prefetch can hurt. Eviction: the prefetched lines push useful data out of L2 — shows up as a cliff at a capacity boundary. Interference: the prefetch traffic competes with the loop's own loads for the same cache and bus — shows up from the first non-zero lead and is absent when the data is already hot. #113's four-row column is the second (rule 31).
lever cell / row of record
Contract §4.2: a variant measured against a sitting's control is a lever cell and never becomes BENCHMARK's "now", however large its win; the "now" (the row of record) is always a sitting's own variant A. So D192 (a lever in #113) became the "now" only as #117's A, and the VTCM feed (+29–32 % as #117's B) became the "now" only as #120's A — an unset run of d79c0efe, 35.97 / 35.96 / 35.17 — read against A0 = NNTR_MOE_HTP_GEMV_FEED=0 (+25.7 %). #120's B, the upstream sync, is a lever cell and stays one.
libnative (HVX emulation)
A C implementation of every HVX intrinsic shipped with the Hexagon tools; PR #107 builds the real GEMV source on x86 against it, so its bit-identity is checked on the workstation, not only on the phone.
lane / lane time
One HVX worker in the DSP's pool (6 on v79). On the GEMV path the profile's swiglu column is the sum of all lanes' busy time, so swiglu / mm ≈ 5.7 = lanes busy over mm (5653.8 / 980.9 = 5.76 on #100's device row; LEDGER, the first rule 24).
LEDGER / BENCHMARK
docs/htp_moe/LEDGER.md: rules learned on silicon, verdicts, open items; BENCHMARK.md: goals and every measured row.
LFM2.5-8B-A1B
The model: 8 B parameters total, ≈ 1 B active per token (top-4 of 32 experts).
lm_head
The final projection to vocabulary logits; tied to the embedding (same matrix, 128000 × 2048).
M, K, N
Matrix shapes: M rows of activation, K reduction length, N output columns. Expert gate_up: M × 2048 × 3584.
M0-PROF
NNTR_M0_PROFILE=1's ARM-side per-MoE-layer stage line.
marshalling
Packing call arguments for FastRPC; #77 B's first name for the transport cost. #88 showed the arguments themselves are 464 bytes and cheap; the cost was cache maintenance on the staging buffers plus the poll window.
M=1 GEMV path (NNTR_MOE_HTP_M1_GEMV, moe_set_opts)
PR #86's branch inside the MoE kernel: at M ≤ 4 the four experts run on the HVX GEMV with no HMX; enabled per session by the IDL method moe_set_opts; on by default since PR #108 (2026-09-22), NNTR_MOE_HTP_M1_GEMV=0 opts out. PR #115 added the lead and the loop to the same word (NNTR_MOE_HTP_GEMV_LEAD_KB, NNTR_MOE_HTP_GEMV_ROWS1; D192 the default), PR #118 the feed (NNTR_MOE_HTP_GEMV_FEED; VTCM the default); the app always sends all three and prints the echo: [HTP] moe m1 gemv: on (applied=0x303e1) lead=192KB rows1=1 feed=vtcm source=default with nothing set. Measured in #94 as variant C: +6.2 / +7.7 / +1.7 % decode, text identical, dsp 1414 → 1044 µs but mm 783 → 975 µs (LEDGER ⑯); as the default in #100 against the same binaries switched off: +13.5 % at G=64, transport +101 µs (later shown to be the arena read's, rule 35); D192 in #113 / #117; the feed in #117 (mm 676, +29–32 %). Prefill (M > 4) never takes the branch.
md5
Checksum used to identify every pushed binary and model file.
mm
Profile column: HMX instruction issue time, timed by difference.
MoE
Mixture of experts: a router picks a few experts per token; here top-4 of 32 in 22 layers.
NDK
Android Native Development Kit: the ARM cross-compiler (r30 here).
NPU
Neural processing unit; in this project the HTP.
ns_per_tile
The microbench's time per 32 × 32 weight tile, summed over lanes; lower is better (#105: 111.72 four-row, 120.23 one-row with the 192 KB lead, 31.25 L2-hot; #113 on the arena: 133.51 four-row, 129.05 one-row + 192 KB, 282.34 four-row + 192 KB).
packed vs strided (VTCM writes)
Where a DMA descriptor's rows land in VTCM: strided = destination stride equals the source stride (the kernel: an expert's eight gate/up chunks tile one 3.67 MB window exactly once); packed = destination stride equals the row size (the probe, and the replay before #99: rows contiguous, chunks overlapping in 569 KB). The DDR read is the same either way; only the write geometry and the checksum footprint differ (plan 99 §3).
paced / unpaced replay
pace=1 replays the descriptors at the traced in-situ wait points (reproduces the in-call 15.6–18.6 GB/s); pace=0 issues them as fast as the ring allows (40.2 GB/s in #94, the row-h number; 31.4 in #100 and 31.2 in #113, cold, on the same unit and code — the anchor cell; the drift is persistent and 31–32 GB/s is the bound, rule 32).
one-row GEMV (gemm_row1)
#105 / PR #107's inner loop for a single activation row: one accumulator, 8 vrmpy per weight tile, the same accumulation order as row 0 of the four-row loop (gemm_rows4), so the int32 sums are identical by construction. The four-row loop at one row issued 32 vrmpy per tile, 24 of them wasted, in a pattern the v79 manual lists as an accumulator stall (36 vs 11–13 packets per tile). (LEDGER ㉒ spells it gemm_rows1; the plan and the PR use gemm_row1.) Measured in #105: 2.26× faster when the weights are L2-hot, slower from the arena unless the prefetch lead is long; #113 confirmed it and measured the whole lead sweep. PR #107 closed; its loop lands through PR #115 as the default (with the 192 KB lead: D192), selectable at run time by NNTR_MOE_HTP_GEMV_ROWS1.
one call per token
The target shape: the whole layer stack resident on the DSP so a token costs one FastRPC round trip (LEDGER ⑨). The entry exists since PR #119; the residency does not — see forward entry and resident (op).
off-tree
Measured on a tree other than htp_moe (for #95: htp_hadamard); recorded in the LEDGER, never compared with htp_moe rows.
pcycles (HAP_perf_get_pcycles)
The DSP's processor-cycle counter. PR #119's forward brackets every op it runs in it (op_pcycles[], returned by forward_debug and summed in the FARF line); a cycle count, not microseconds — the MoE stage table stays in µs.
PD (unsigned PD)
Process domain on the DSP; "unsigned" lets a non-signed skel run.
poll QoS (qos_mode=2) / poll window
After sending a call the ARM thread can poll — check for the reply over and over, fast but keeping a core busy — or sleep until an interrupt wakes it, cheap but slow to wake. The poll window is how long it polls before sleeping: 5000 µs since PR #103 (NNTR_HTP_POLL_US, was 100 µs, which every ≈ 1.4 ms decode call outlived; worth 67.6 µs per call in #88). qos_mode=2 in the profile header = poll accepted; 1 = the driver refused the value (10 000 is refused) and fell back to PM QoS.
PPL (perplexity)
How surprised the model is by a known text, averaged per token; lower is better. NNTR_PPL prints the prompt's teacher-forced perplexity at prefill (upstream 32b46e32, in htp_moe since PR #121 merged on 2026-09-27); #95 used it as the accuracy measure (115.1 → 100.5 with the Hadamard rotation).
per-unit DMA bound (rule 34)
See "session drift". The single-queue DMA rate differs between two S25 Ultras (37.3 vs 31.2 GB/s) while the vector unit's direct DDR read does not; the anchor cell names it per sitting.
per-token budget
LEDGER §2's split of one decoded token into MoE DSP time, transport and "outside the MoE call", derived from tok/s minus 22 × the profile row — an estimate, not a measurement. Cycle 16, on #120 A (the feed default as a control), G=512: 27.81 ms = 15.7 / 1.8 / ≈ 10.3; earlier 27.40 on #117 B (15.7 / 2.0 / 9.7), 35.86 on #117 A (21.9 / 4.2 / 9.8), 36.9 on #100 A (22.9 / 4.1 / ≈ 9.9), 37.2 on #105 A (22.7 / 4.0 / ≈ 10.5), 42.0 on #88 B (30.4 / 1.9 / ≈ 9.6). The outside term has read 9.7–10.3 in its last four derivations.
prebind
Plan 88's conditional step (per-layer handles bound once); not built, because #88 met the ≤ 0.1 ms gate without it.
PR (#4327)
The upstream pull request this branch is frozen from; its docs are docs/htp_attention/*.
prefill
Processing the prompt (512 tokens) in one pass; M ≫ 1; the −5 % gate on every change.
profile build (--profile)
An app build that prints per-node totals; never read for tok/s (rule 1).
qkv fusion (qkv_layer)
Upstream 1f538c20 (in the #120 sync, PR #121, merged 2026-09-27): LFM2's q / k / v projections and their norms as one CPU layer — the same three GEMMs and norm kernel, reading the unchanged weight order (q, q_norm, k, k_norm, v). Always on in B; #120 read its text identical to A's at every G.
Q4_0
4-bit block quantization (32 weights per scale) the CPU kernels read.
QS4CX / QS4CX_WH
4-bit per-channel quantization; the WH variant is pre-arranged in HMX tile order and has no CPU path.
region (arena region)
One 256 MiB ION chunk of the arena as seen by the DMA engine; the M=1 list touches 32 per call (regions=32 in the replay is its fresh=1 rotation pool, not the expert count — plan 99 §3).
row h
The eighth row of plan 87's wall-2 attribution table, added by the device in #94: the real chunk list looked slow on its own (40 vs 107 GB/s), ≈ 60–70 % of the isolated-vs-in-situ gap. Dissolved by #100 (2026-09-23): the 107 was a probe number no checked per-call path reproduces; against the validated c_star the list is 1.19× faster (rule 28; rule 19 withdrawn).
session drift (rule 30) → per-unit DMA bound (rule 34)
One unit's DMA rate moving between sittings on identical code: the unpaced one-worker replay read 561.5 µs per call in #94 and 719.6 in #100 (1.28× slower), not thermal, biting single-queue issue rate rather than aggregate bandwidth; cause not separated. Resolved by #113 (rule 32): the cell read 724.0 µs / 31.2 GB/s cold again, so the drift is persistent and 31–32 GB/s is that unit's real bound. Qualified by #117 (rule 34): the same cell reads 607.9 / 605.3 µs (37.1 / 37.3 GB/s) on the second S25 Ultra, R3CY10WM83Y, while the HVX direct arena read (D192's mm) is the same on both phones — the difference sits in the DMA engine or its clock, and three anchor values exist (40.2 once, 31.2–31.4 twice, 37.1–37.3 twice). So an absolute mm gate on a DMA-fed path is read next to the sitting's anchor, a DMA-fed path's win is unit-dependent, a direct-read path's is not, and the goal's ceiling is per unit (484 MB of MoE weights per token = 13.0 ms at 37.3, 15.5 at 31.2).
resident (op)
An op of the decode graph description whose kind has a non-NULL slot in the DSP build's kernel table (hexkl_graph.c kernels[]), so forward may run it. Today only MOE is resident; the validator refuses a resident bit on any other kind (AEE_ECLASSNOTSUPPORT). The call count per token falls only when every op between two MoE ops is resident (LEDGER's second ㉓ row).
resume_at
What forward returns: the index of the first op it did not run (not resident, or past the list). With MOE the only resident kind it is always start_op + 1, and the ARM throws on anything else.
RMSNorm
Root-mean-square normalization, before each mixer and each FFN.
RoPE
Rotary position embedding applied to q and k in attention.
router / top-k
The small FP32 matrix and the sigmoid + bias ranking that choose 4 experts and their weights.
RPC
Remote procedure call; see FastRPC.
RSS (peak memory)
Resident set size the app reports at the end of a run, in KB.
rung / gate
The verification ladder: 0 format, 1 host build + checks, 2 skel, 3 Android app + device gtest, 4 device handoff.
SDK (Hexagon SDK 6.4.0.1)
Qualcomm's DSP toolchain.
SiLU / SwiGLU
silu(x) = x · sigmoid(x); SwiGLU = silu(gate) · up, the FFN's non-linearity.
ride-along
A few extra cells a PR without its own sitting appends to the next handoff (PR #108's R1–R4 go into #100's).
slab (VTCM slab, G0 / G1)
#117's two gate_up-sized (3.5 MiB) regions of VTCM at offsets 0 and gu_bytes, which double-buffer stage A by expert: expert i's gate_up lands in slab i & 1, and once a slab has no gate_up left to hold, two down matrices (1.75 MiB each) land in it (down of expert j in slab (j >> 1) & 1, half j & 1). Every push is a whole matrix in one descriptor (f2's shape, 8 per call at top-4) and every reuse of a slab follows the join of the pool run that read it. The M=1 path used no VTCM before, so the whole ≈ 8 MB arena was free; a shape whose two slabs do not fit falls back to the arena read (hexkl_mm_u8i4_moe.c:440–466, moe_m1_gu_off / moe_m1_dn_off).
scoreboard (host)
The host check in test/htp/host/moe_layer_host_check.c that replays #117's slab schedule on the workstation and proves that no slab is overwritten before the pool run reading it has joined — the reason the kernel runs one pool run per expert and stage (six extra fork/joins a call, a ponytail: note names the upgrade if the tail ever shows; the vtcm microbench found none).
size-class staging
Upstream's fix (fb0f02b9, in htp_moe via PR #103): one cached ION staging buffer per power-of-two size from 64 KiB, picked per call, so a decode call rides a 64 KiB pair instead of the 4 MiB pair the prompt grew — the driver's whole-buffer cache maintenance shrinks with it (245.8 µs per decode call in #88). Both classes stay allocated (+0.3 % peak RSS).
staging: line
Profile line (level ≥ 2, since PR #103) under each MoE row: the size classes the call rode, ion=y|n, rpc allocs (process-wide count of shared buffers; must not grow with calls) and the argument bytes copied outside ION (464 at decode).
same-unit drift
How much one phone's tok/s moves between sittings with no code cause: up to −16 % (NPU) / ±9 % (CPU) per cell in #94 vs #77 while the DSP profile columns moved ≤ 4 % (LEDGER rules 9, 20). Recorded as a note, never as a verdict.
sitting
One uninterrupted session on the phone; the unit within which numbers are comparable.
SNR
Signal-to-noise ratio in dB between two paths' outputs; NNTR_L2_DIFF's accuracy measure, the gate for #95.
subnormal / FTZ
Floats too small for the normal exponent range; FTZ ("flush to zero") replaces them with 0. v79's HVX IEEE float arithmetic keeps them, so a scalar reference for HVX code must not flush (LEDGER, the second rule 24, #95).
tag / tag sum (tag=N/N)
PR #112's content check for a replay cell: the DSP sums a byte pattern over every push's VTCM window and the host computes the same sum from the plan; equal = the list landed where the plan says (res[12], unittest_hvx_dma_probe.cpp:647–715). stale_skel_or_nothing_landed = the skel on the device does not carry the #100 entry.
SMMU
The IOMMU that maps ION buffers into the DSP's address space.
stage
Profile column: DMA copies of the activation in and the output out of the ION buffers.
thermal_zone0
The phone's SoC temperature sensor the handoff samples at each checkpoint (29 °C cool → 51–55 °C after the twelve A cells in #94); probe readings are quoted with it (rule 18).
transport (wall 3)
The FastRPC round trip of one call, host − dsp. Closed as a wall by #88 (401.3 → 87.9 µs per decode call, 1.9 ms per token); 82.2 µs at the feed default as a control (#120 A: 1.8 ms per token). Only comparable inside one sitting (rule 23).
tok/s, TPS
Tokens per second; the app prints "TPS".
UND symbols / undefined-symbol guard
UND is readelf's mark for a symbol a shared object imports rather than defines. A Hexagon skel legitimately imports ~46 runtime symbols (HAP_*, qurt_*, libc…) that the DSP image resolves at load; a project symbol left UND (a .c missing from build.sh) links fine and fails only on the device with 0x80000406. Since PR #98 build.sh checks this and prints UNDEFINED SYMBOLS OK (<n> runtime imports) (LEDGER rule 17).
unit
A specific phone, identified by its adb serial. Since 2026-09-22 no particular unit is required (contract §12): a handoff names none, the filled handoff records the one used. Every nntrainer row up to #113 ran on R3CY205ZMND (#77, #94, #88, #105, #100, #113); #117 and #120 ran on R3CY10WM83Y, the user's second S25 Ultra (both SM-S938N, SM8750); the PR author's rows are from R5KL30G6MLT. Two S25 Ultras were 6–8.6 % apart in tok/s on one binary in an earlier project (rule 10), and #117 measured the two units' DMA engines 19 % apart on an untouched cell (rule 34), which is why numbers are compared only inside a sitting (rule 13).
variant A / B / C, A0
A = the unchanged control binary that opens every sitting; B, C = the variants read against it; A0 = the same binaries as A with the previous default restored by an environment variable (the same-sitting proof of a landed default). In #94, C was the same binary with the M=1 GEMV switch on; in #88, B was PR #103 and C was B with the poll window back at 100 µs; in #105, B1–B3 were PR #107's skels with prefetch leads 0 / 64 / 192 KB; in #100, A0 was NNTR_MOE_HTP_M1_GEMV=0 (24.58 vs A's 27.89 tok/s at G=64). #113 named its cells A (four-row, lead 0), B (four-row, 192 KB), C (four-row, 384 KB = L*), D (one-row, 384 KB) and added D192 (one-row, 192 KB) mid-sitting; only A and D192 ran end to end. #117: A = the D192 default reading the arena (0x103c1), A0 = LEAD_KB=0 ROWS1=0 (0xc1, #113's confirmation), B = the VTCM feed (0x303e1). From PR #118 on, A is the feed default (0x303e1 feed=vtcm) and A0 is NNTR_MOE_HTP_GEMV_FEED=0 (0x103e1 feed=arena) — #120 ran exactly that: A 35.97 / 35.96 / 35.17, A0 28.62 at G=64, and B = the upstream sync on its own skel (37.68 / 36.29 / 35.10).
sub-gate win (rule 33)
The user's decision rule of 2026-09-23: a change that misses its issue's gate may still become the default when its decode gain is consistent at all three G in one sitting, the text is byte-identical and the prefill gate holds; the issue's gate still says whether the issue is done. First applied to D192. Not enough: a win at one G, a win inside the sitting's own A spread (rule 27), or one bought with a text change.

v79
The Hexagon architecture version in the Snapdragon 8 Elite.
vrmpy
HVX multiply-accumulate of four u8 × i8 products per lane; the GEMV's inner instruction.
VTCM
Vector tightly-coupled memory: 8 MiB of on-chip SRAM the HMX reads from; filled only by DMA.
wall
One of the three measured limits of the decode MoE call: HMX 64-row tile (fallen with the GEMV; its residue, the weight feed, fixed by #117's VTCM feed — the default since PR #118; ≈ 1.9 ms/token of engine gap left on a fast unit, ㉓), weight DMA rate (dissolved as a list question by #100; the engine bound is per unit — 31–32 GB/s on one phone, 37 on the other, rules 32 / 34), FastRPC transport (closed by #88; the GEMV path's extra ≈ 100 µs turned out to be the arena read's and left with the feed, rule 35). What is left after the walls is outside the call: transport 1.8 + CPU work ≈ 10.3 = 12.1 ms/token at G=512 against a ≈ 6.5 ms floor (cycle 16, #120 A; ⑨, one call per token — its skeleton is PR #119, merged, still 22 calls).
WH tile
"Weight, HMX order": 32 k × 32 n int4, 512 B, the layout the HMX (and the HVX GEMV) reads.
worker pool
DSP threads with HVX contexts (one fewer than the contexts the DSP reports; the calling thread is the extra lane) that run epilogues, requant and scatter behind the HMX, and the GEMV's column units.
zp (zero point)
The offset of an asymmetric u8 quantization, per row, alongside its scale.
