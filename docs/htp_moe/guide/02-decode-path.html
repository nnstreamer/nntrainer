Decode means: the prompt has already been read (prefill), and the model now produces one token, feeds it back, produces the next, and so on. Every step below is repeated per token. The shape that matters everywhere is M = 1: one activation row goes through every matrix.

2.1 One token through the 24 layers

The new token's embedding row (Q4_0, 2048 wide) enters layer 0. Each layer is a mixer followed by a feed-forward block, each wrapped in an RMSNorm and a residual add. There are two mixer kinds and two feed-forward kinds:

  • Conv mixer (18 layers). rms_norm → in_proj (a fully-connected matrix to 3 × conv width) → split into three → custom_multiply (gate B) → causal_conv1d (a short depthwise convolution over the last few positions) → custom_multiply (gate C) → out_proj (fully-connected back to 2048). lfm2_causallm.cpp:152–201
  • Attention mixer (6 layers). q/k/v projections, per-head norm (reshaped_rms_norm), rotary position encoding (RoPE, rope_theta at lfm2_causallm.cpp:130), mha_core over the KV cache, o projection.
  • MoE FFN (22 layers). rms_norm → router → 4 of 32 experts → weighted sum. This is the block that runs on the DSP (§2.2). lfm2_causallm.cpp:212; contract §1
  • Dense FFN (2 layers). gate/up FCs → swiglu → down FC, on the CPU.

After layer 23: output_norm and the tied lm_head (output_of_causallm, 128 000 × 2048, Q4_0) give the logits; greedy decoding picks the argmax. lfm2_causallm.cpp:404; contract §1 "tied lm_head"

2.2 The MoE call, step by step

a. Router (ARM)

The normalized row x (2048 floats) is multiplied by the router matrix (FP32, 32 columns, on the CPU) to get 32 logits. For each expert the code takes a sigmoid; adds a per-expert bias only for ranking; keeps the top 4 by (sigmoid + bias); and sets each chosen expert's weight to its bias-free sigmoid divided by the sum of the four (then a fixed scaling factor). lfm2_moe_layer.cpp:271–312 (buildExpertAssignments), :774 (input.dot(gate_weights))

b. The gate: who runs the experts

tryMoeLayerOnAccelerator decides. If the expert weights are QS4CX_WH, the DSP path is taken even at one token, because no CPU kernel can read that layout. With plain QS4CX weights a single token would stay on the ARM (the 64-row padding does not pay) unless NNTR_MOE_HTP_DECODE=1. lfm2_moe_layer.cpp:455–506

A second switch decides which kernel path the DSP takes once the call arrives, and how that path is fed. NNTR_MOE_HTP_M1_GEMV is read once on the ARM and sent once per session through the IDL method moe_set_opts; the DSP stores the word and decides per call on M (§2.2 e′). Since PR #108 (merged 2026-09-22) the GEMV path is on unless the variable is 0. Three tuning knobs ride in spare bits of the same word, each authoritative only when its own "set" bit is on, and the ARM always sends all three (its own copy of the defaults when the environment names nothing) so that every log's echo names the cell that ran: the l2fetch lead (bits 15:8, in 64 KB units, set bit 7; NNTR_MOE_HTP_GEMV_LEAD_KB, default 192), the one-row loop (bit 16, set bit 6; NNTR_MOE_HTP_GEMV_ROWS1, default 1 — PR #115), and since PR #118 the weight feed (bit 17, set bit 5; NNTR_MOE_HTP_GEMV_FEED, default 1 = DMA each expert into VTCM, 0 = read the arena). The DSP echoes the word back and the ARM prints it to stderr as the proof of the path a tok/s run took; with nothing set the line is [HTP] moe m1 gemv: on (applied=0x303e1) lead=192KB rows1=1 feed=vtcm source=default (source=env when NNTR_MOE_HTP_M1_GEMV itself was set; off for the opt-out). NNTR_MOE_HTP_GEMV_FEED=0 prints 0x103e1 … feed=arena (the D192 arena read, #117's A); LEAD_KB=0 ROWS1=0 FEED=0 prints 0xe1 (the pre-#115 four-row, no-lead cell). c. Routing arrays and staging (ARM)

The four (expert, weight) pairs become three arrays in expert order: row_index (which token row — at decode always row 0, four times), row_count[32] (1 for the four chosen experts, 0 elsewhere) and row_weight. The activation row (2048 floats = 8 KiB) is copied into a shared ION buffer the DSP can see; the output goes to another. Expert weight handles (small integers registered at load) are looked up from a cache. lfm2_moe_layer.cpp:524–545; htp_compute_ops.cpp:1723–1731

Which buffer, since PR #103 (#88): one per size class. Before, the app kept one activation buffer and one output buffer and grew them to the largest call ever seen (ensureCapacity) — after a 512-token prompt, 4 MiB each — and every later call reused them. Now stage() keeps a separate buffer for every power of two from 64 KiB up and hands each call the smallest one that fits: decode rides a 64 KiB pair, prefill a 4 MiB pair, and both stay allocated. d. FastRPC round trip

The session itself is opened once at load: an unsigned process domain on the compute DSP (cdsp), then a latency setting for poll mode (RPC_POLL_QOS, fallback PM_QOS); that is the qos_mode=2 in every profile header. htp_backend.cpp:40–110

Two costs hide in the round trip besides the work itself (plan 88's inventory, confirmed by #88's sitting):

  • Keeping the shared buffers consistent. The staging buffers are cached ION memory: the ARM writes the activation into its cache, so before the DSP reads it the driver must write the cache back to DDR (clean), and before the ARM reads the output it must drop stale cache lines (invalidate). The driver does this over the whole buffer, not the bytes passed — about 36–59 µs per MB on the PR author's phone. With the old 4 MiB pair every decode call paid for 8 MiB of cache maintenance to move 16 KiB. Size classes shrink that to two 64 KiB buffers.
  • How the ARM waits. After sending the call the ARM thread can poll — check the reply flag over and over in a tight loop, which notices the answer within microseconds but keeps a core busy — or sleep and be woken by an interrupt, which is cheap for the CPU but slow to wake. The poll window says how long to poll before switching to sleep. It was 100 µs; a decode call lasts ≈ 1.4 ms, so every call ended on the slow interrupt path. Since PR #103 the window is 5000 µs (NNTR_HTP_POLL_US), so the ARM is still polling when the DSP finishes.

Measured in one sitting (#88, M==1, profile level 2, µs per call): control A 401.3; C = the fixed binary with the poll forced back to 100 µs 155.5; B = both fixes 87.9. So of the 313.4 µs removed, 245.8 (78 %) is the staging and 67.6 (22 %) the poll. The remaining 88 µs is 6 % of the 1471 µs call and the 464 argument bytes are already the floor, so the planned "prebind" of per-layer handles was not built. docs/plans/88-moe-call-marshalling.md "What the 528 µs are", §2.1; 88-moe-call-marshalling.md Transport table and Verdict; LEDGER ⑦; htp_backend.cpp:76–92; doc 50 §3.6 via plan 88

e. On the DSP (hexkl_mm_u8i4_moe_layer_run): the HMX path

This is the path the PR shipped with; since PR #108 a decode call takes the vector-unit branch of e′ instead, and the HMX path serves prefill and the NNTR_MOE_HTP_M1_GEMV=0 opt-out. Steps 1–4 and the stage-out are shared.   1. Validate and lay out. Every handle's K/N is checked before any work; VTCM (the DSP's 8 MiB on-chip scratch memory) is carved into fixed regions: activation block 128 KB, gate_up weights 3.5 MiB, down weights 1.75 MiB, gate f32, mid u8, two 256 KB accumulator staging buffers, result f32. :490–571, :597–613; doc 49 §4.4
  2. Stage in [stage 4.4 µs]: DMA the activation row from the uncached ION buffer into a cached DSP-heap copy act_c; zero out_c. :807–809
  3. Kick the first weight DMA. Expert 0's gate_up (3.5 MiB) is pushed from the ION arena (where all 1408 expert weights sit in DDR, in HMX tile order) into VTCM through a ring of 2D DMA descriptors, in four column chunks. :823–827, moe_push_gate_up_chunks :159; hexkl_dma_ring.c
  4. Activation quantization [quant 21.9]: the row's min/max give a scale and zero point; the row is packed as u8 into the "AH" tile layout the matrix unit reads. Each active expert gets a 64-row slot block; at M = 1 the other 63 rows are padding that repeats row 0. :831–872
  5. Per expert (4 times):
    • [gather 122.6] wait for the activation block DMA and copy the block's scale/zp;
    • push the expert's down weights (1.75 MiB) so they arrive during gate_up;
    • [drain 0.9+0.4] wait for the gate_up chunk;
    • [mm 746.6 + acc 258.8] HMX gate_up: for each of 112 column tiles, clear the accumulator, issue 64 tile multiplies (64 rows × 32 k × 32 n each), read the 64×32 int32 result out to staging. 63 of the 64 rows are padding at decode;
    • [dequant 7.3, swiglu] worker threads dequantize gate and up tiles (scale · column sum · bias) and store silu(gate) · up as f32;
    • [requant 41.9] the 1792-wide f32 row becomes u8 again for the down matrix (synchronous, nothing to hide behind);
    • HMX down (same shape rules, 64 column tiles) → dequantize to f32;
    • [scatter 0.9] out_c[row] += weight · result — the weighted sum of the four experts is this +=. :976–1225; doc 49 §3.2.2 "scatter"
  6. Stage out: DMA out_c back to the ION output buffer; return. :1230–1246

e′. The M = 1 path on the vector unit (PR #86; the decode default since PR #108; one-row loop + 192 KB lead since PR #115; fed from VTCM by DMA since PR #118)

This is what a decode MoE call runs today. Wall 1's fix lives inside the same kernel as a branch taken right after the activation scan: when the session flag is set (the default since PR #108) and the call has at most 4 rows, at most 4 rows per expert and 1–16 active experts, the HMX loop and every weight DMA are skipped and the four experts go through the HVX matrix-vector kernel (hvx_gemm_u8i4_wh_col, the one the prefill "tail" path already used). Where the 975 µs go — measured by #105 (2026-09-22). Reading the compiled inner loop, plan 105 found that at one row the kernel still runs the four-row loop: per 32×32 weight tile it issues 32 vrmpy multiply-accumulates (only 8 are for the real row) rotating over four accumulators, and each column's l2fetch prefetch goes out right before the loads that need it. PR #107 replaced it with a one-row loop (gemm_row1, the same accumulation order, so bit-identical by construction) and a prefetch lead, so each lane fetches its next block of columns early (0, 64 or 192 KB ahead: variants B1, B2, B3). A microbench, MoeM1GemvFeedVsCompute, runs the same kernel on three copies of the weights — the ION arena, the ordinary DSP heap, and a set small enough to stay hot in the L2 cache — so the hot cell shows the arithmetic alone and the gap to the arena cell shows the waiting.

What the phone said. The arithmetic got 2.26× faster (hot cell 70.77 → 31.25 ns per tile) — but on the arena the one-row loop was slower without a lead (mm +7.4 %), and even the 192 KB lead only reached −4.3 % (973.0 → 930.9 µs), short of the gate (more than −5 %, and ≤ 600 µs to close the item). Decode moved −8 % to +3 %; text stayed identical in every cell. The reason is the feed: under the one-row loop with the 192 KB lead, ≈ 74 % of mm is waiting for weight bytes (≈ 690 of 931 µs), only ≈ 240 µs is arithmetic. A vector unit that reads DDR directly gets 21–27 GB/s whether the weights sit in the ION arena or in the DSP heap, and with a quarter of the multiply-accumulates in flight the one-row loop hides that latency worse (LEDGER rules 26, 27). So PR #107 was held, not merged, and the plan after #105 was to feed the GEMV from VTCM: DMA each expert's weights into on-chip memory while the vector unit works on the previous one, which needs a DMA shape that moves ≥ 37 GB/s beside the vector unit (22 MB in ≤ 600 µs). docs/plans/105-m1-gemv-compute.md §1, §3; 105-m1-gemv-compute.md Verdict, "What the microbench says"; LEDGER §2 ㉒ row (cycle 9), rules 26–27; plan 100 §0

What #100 said about that feed (2026-09-23), and where the lever moved. #100 built the feed candidates as replay cells — f1 (six contiguous pieces per expert, hvx_impl's shape), f2 (two whole-matrix descriptors per expert, ㉒'s own idea), f3 (the probe-iii column shape written strided so the GEMV can read it) — and ran each with and without an HVX job streaming VTCM at the same time. The vector unit's reads cost the DMA only 0.1–0.3 % (rule 29), but the best shape moved 31.6 GB/s, under the 37.0 gate, and every checked cell in the run sat near 31 GB/s whatever its shape. Two things soften the "fail": the same phone's DMA was 22 % slower that day than in #94 on a cell the PR did not touch (rule 30), so the gate is not closed; and even a passing feed would be ≈ 1.2× the GEMV's own direct read (21–27 GB/s), for the price of a ring and a double buffer. What #113 said (2026-09-23): the lead helps only the loop that needs it, and the feed half is a rate question at 31 GB/s. One gtest run printed the whole 2 × 5 matrix. The four-row loop — the one the phone runs today — is harmed by any lead: on the arena its ns_per_tile goes 133.5 → 282.3 / 316.4 / 323.1 / 328.4 at 192 / 384 / 768 / 1536 KB, damage starting at the very first non-zero lead, while a copy of the weights already hot in L2 is flat (71.7–73.5). A token at G=512 on the "now" — the VTCM feed default, measured as its own sitting's control in #120 — is ≈ 27.8 ms = MoE DSP 15.7 + transport 1.8 + everything outside the MoE calls ≈ 10.3 (LEDGER's cycle-16 estimate: token time minus 22 × the level-2 M==1 host; the same arithmetic on #117's lever B had given 27.4 = 15.7 + 2.0 + 9.7, within 0.6 ms). The contract's shape for ⑨ is M = 1 kernels for the rest of the layer on the DSP (RMSNorm, conv1d + gating, RoPE, attention at M = 1, dense FFN, lm_head) and one per-token entry in the IDL, so the ARM sends one token in and gets logits out with a single round trip — the "DSP owns the graph" shape that the frozen hvx_impl branch already validated for a smaller model.

The decode step is described to the DSP as a flat list of 32-bit words (htp_graph_desc.h): a header, the kind of each of the 24 layers (conv or attention; dense or MoE FFN), then one 76-word record per op — its kind, layer, a resident bit, input and output widths, its two activation slots, the next weight-streaming op, and for a MoE op the 32 gate/up and 32 down weight handles. On the DSP, hexkl_graph.c keeps the table and runs forward as "from the start op, while the op's resident bit is set, look its kind up in the kernel table and call it; stop at the first op that is not resident and report its index", timing every op in HAP_perf_get_pcycles and printing one FARF line per call ([graph] start= resume= ops= pcyc= moe=).
