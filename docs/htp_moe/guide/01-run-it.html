run_host_checks.sh compiles the DSP kernel sources (hexkl_mm_u8i4_moe.c, the worker pool, the DMA trace module) on the workstation against scalar stand-ins of the HVX/HMX primitives and checks the kernel's loop structure and bit-identity to a reference. There is no Hexagon simulator in this project; this host check and the phone are the only two places a kernel is proven. Since PRs #93 and #86 it also prints, and a run is only green with all of them: M1 GEMV PATH BIT-IDENTICAL TO HMX PATH (M=1,2,4; tiny+real) (the M=1 GEMV path of page 2 §2.2 e′ against the HMX stand-in, six shape × M cases — about a minute at -O2), PROFILE ON/OFF BYTE-IDENTICAL and PROFILE OFF: TRACE UNTOUCHED (the DMA trace changes no output byte and costs nothing when profiling is off), IN-SITU CHUNK PLAN MATCHES KERNEL (46 descriptors) (the header-only descriptor planner the replay gtest uses equals what the kernel really pushes at the M=1 LFM2 shape) and DMA TRACE ARITHMETIC OK (the trace's busy/depth/blocked bookkeeping on a scripted sequence). Since PR #108: MOE M1 GEMV OPTS: unset=on 0=off 1=on (what the switch variable resolves to) and MOE PROFILE ROW: gemv rest>=0 hmx unchanged (the fixed profile-row arithmetic, checked on #94 sitting 2's printed rows). 2. The DSP library ("skel"; seconds)

HEXKL_SDK_VER=6.4.0.1 ./test/htp/build.sh   # v79, -Wall -Werror; last lines:
#   UNDEFINED SYMBOLS OK (46 runtime imports)
#   built: .../test/htp/build/libnntr_hvx_skel.so (v79, hexkl 6.4.0.1)
md5sum test/htp/build/libnntr_hvx_skel.so   # record it; every handoff quotes it

libnntr_hvx_skel.so is the code that runs on the DSP. build.sh first runs qaic on test/htp/nntr_hvx.idl — the interface file that lists every remote function (mm_u8i4_moe_layer, arena_attach, …) — which generates a stub (ARM side, calls into the DSP) and a skel (DSP side, receives the call), then compiles the kernels under nntrainer/tensor/htp_backend/{hmx,hvx}/ and test/htp/*.c into the skel — since PR #119 (2026-09-23) that list includes hmx/hexkl_graph.c and test/htp/nntr_hvx_graph.c, the per-token entry behind NNTR_HTP_FORWARD (§7 below), and a skel built before it answers the four graph entries with AEE_EBADPARM. Since 2026-09-27 the list also carries upstream's hmx/hexkl_conv_block.c and hvx/hvx_conv_gate_f32.c (PR #121), hvx/hvx_m1_ops_f32.c with test/htp/nntr_hvx_small_ops.c (PR #125) and hvx/hvx_attn_m1_f32.c with test/htp/nntr_hvx_attn_m1.c (PR #126), and the IDL grew by mm_u8i4_conv_block, the three small-op test entries rmsnorm_det_f32 / rope64_det_f32 / conv_gate_m1_f32 and attn_m1_register / attn_m1_release / attn_m1_kv_append / attn_m1_forward — so a skel from before the merge answers any of them with 0x8000040e, and no md5 of a post-merge skel has been recorded yet (LEDGER §3a). Since PR #98 (2026-09-22) the script ends with a guard: it reads the skel's dynamic symbols with hexagon-readelf and rejects any undefined name outside the runtime imports the DSP image provides (HAP_*, compute_resource_*, qurt_*, libc, compiler-rt, memalign). A clean build prints UNDEFINED SYMBOLS OK (<n> runtime imports) — 46 on every recorded build up to #120's skels; a post-#121 skel's count is not recorded yet; otherwise it lists the offending names and exits 1, and an empty list (readelf missing) is also an error, so the check cannot pass vacuously. Rung 2 of the gates is not green without that line. Set HEXKL_SDK_VER=6.4.0.1 explicitly: with it unset the script picks the newest directory under $HEXKL_ROOT/lib, and a workstation with 6.6.0.0 installed would silently link another HexKL. hexagon-gates §2; test/htp/build.sh:77–87, 110–131; test/htp/nntr_hvx.idl:524–600; PR #98 body; LEDGER rules 17, 21, §3a

Trap. build_android.sh never rebuilds the skel. Whenever the IDL or any DSP source changes, run test/htp/build.sh again and push the new skel. A stale skel fails on the phone with AEE_EBADPARM (0x8000040E). LEDGER rule 3
This bit twice on 2026-09-22: PR #93 added the IDL entries moe_dma_trace_read and dma_replay and ten stage slots to the timed MoE call, PR #86 added moe_set_opts and one more slot (30 in total), so an app and a skel must come from one commit. An old app with the new skel (or the reverse) fails on the first MoE call with AEE_EBADPARM; and since PR #108 made the GEMV path the default, the new app with any skel older than moe_set_opts throws nntr_hvx_moe_set_opts failed … rebuild it at the first MoE call unless NNTR_MOE_HTP_M1_GEMV=0 is set — on purpose, so a run can never report the HMX loop as the GEMV. test/htp/nntr_hvx.idl:409, 437, 449; test/unittest/unittest_hvx_dma_probe.cpp:512–515; htp_compute_ops.cpp:1102–1143; 101-ride-along.md; BENCHMARK.md "Artifacts" #94 rebuild note
Troubleshooting: three loader errors that look alike.
  • AEE_EBADPARM (0x8000040E) on the first MoE call, or DMA_REPLAY_NOTE moe_layer_timed err=0x8000040e in a gtest — the skel loaded but does not match the app's IDL (stage-slot count, new entries): stale skel or stale app, rebuild both from one commit and re-push (rule 3).
  • 0x80000406 from remote_handle_open_domain, logcat dlerror RX VA 0xFFF00000 outside ELF segment — the skel itself does not load. Despite the wording this is not a segment-layout bug: a Hexagon shared object links with unresolved symbols by default, -Wall -Werror stays clean, and the on-device loader is the first thing that refuses the image. This blocked every NPU cell of the first #94 attempt on 2026-09-22: PR #93 had added hmx/hexkl_dma_trace.c to the host checks but not to SRCS in build.sh, so the skel carried seven undefined hexkl_dma_trace_* functions (#97, p0). PR #98 added the file and the UNDEFINED SYMBOLS OK guard above; sitting 2's first device command (DmaProbeShapes PASSED) was the acceptance. If you see 0x80000406 today: check the two md5sum lines (stale skel on the device), then hexagon-readelf --dyn-syms libnntr_hvx_skel.so | awk '$7=="UND"' for a project symbol (hexkl_*, hvx_*, nntr_*) — a new .c under htp_backend/ that never entered build.sh is the first suspect. Otherwise it is a new loader fault: file an issue with logcat attached.
  • [Engine] htp Context is not registered — app-side, before any DSP call: the htp context is registered only when the app was built with ENABLE_HEXKL, i.e. build_android.sh --htp (§3; the readelf line there is the quick test). The skel is not involved.

7. Run one decode

adb shell "cd /data/local/tmp/nntrainer/causallm && \
  NNTR_NUM_THREADS=8 LD_LIBRARY_PATH=. ADSP_LIBRARY_PATH=. \
  ./nntrainer_causallm ./models/q40-qs4cx-wh \"\$(cat prompt512.txt)\""
  • ADSP_LIBRARY_PATH=. tells the FastRPC driver where to find libnntr_hvx_skel.so for the DSP. LD_LIBRARY_PATH=. finds libsdkl.so and the nntrainer libraries.
  • NNTR_NUM_THREADS=8 for both CPU and NPU runs — every number in this project is measured that way. contract §1.1
  • prompt512.txt is a text that tokenizes to exactly 512 tokens (docs/measurements/77-prompt512.txt, on htp_moe since cycle 10, md5 fc65c158…). Run the CPU model first: its decode rate is the thermal gate (CPU decode < 30 tok/s means the phone is throttling — cool down and redo). 77-first-handoff.md step 2

Reading the output

After the generated text the app prints a fixed block (from Applications/CausalLM/models/causal_lm.cpp:699–710):

=================[ LLM with NNTrainer ]===================
prefill: 512 tokens, 1054 ms, 485.769 TPS
generation: 512 tokens, 27861 ms, 18.3756 TPS
total: 28915 ms
peak memory: 5323824 KB
==========================================================
  • prefill: — tokens in the prompt, the time to process them, and tokens per second. The count must read 512; anything else means a tokenizer mismatch and voids the prefill column.
  • generation: — tokens generated, wall time, and decode tok/s over the whole generation. This is the number the goal is read against. The count must equal num_to_generate.
